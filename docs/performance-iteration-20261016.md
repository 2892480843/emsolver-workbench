# 2026-10-16 架构与数据访问性能迭代

## 目标与范围

用户已授权持续优化。本轮聚焦单机工作台的请求并发、查询边界及关联数据结构，保持 SQLite schema 2、旧接口、项目权限、求解算法与结果认证规则。环境已核实为 macOS arm64；测试与基准使用临时目录，不向业务库注入合成记录。

采用现有模块化单体：HTTP 接口负责异步调度，应用服务负责授权，Store 负责参数化的索引查询，数值任务仍在独立进程运行。先减少重复访问与无关正文解析，后续按实测需要再调整实体表示及锁范围。

## 测量原则

- 查询数、JSON（结构化正文）解码数量与响应一致性是确定性检查；耗时采用多轮、交错、热缓存诊断，报告分布和环境。
- 并发测试使用可控的阻塞提交验证事件循环是否仍可服务其他请求；这是并发回归，不是磁盘导入吞吐量测试。
- 临时合成库衡量扩大历史数据后的行为，不代表工业矩阵求解速度。实际工作区当前只有 8 个矩阵和 41 个任务，前端关联索引收益有限。
- 不跨请求缓存权限，不改变分页游标和动态状态总数，不新增数据库迁移及外部服务依赖。

## 下一轮候选

1. 任务分页增加兼容的摘要表示，减少轮询中的完整结果和运行能力信息传输；完整详情仍由现有详情请求提供，避免认证及对照字段丢失。
2. 评估导入哈希移出写事务的方案，先明确文件所有权、取消、并发注册和失败清理，再缩短互斥锁占用。
3. 评估基准批次列表的任务关联读取；按请求范围批量读取，避免展开后再丢弃完整结果。
4. 分别建立导入吞吐、接口并发与数值求解的性能预算；只有新瓶颈得到复现后才继续扩大改动范围。

## 已验证结果

以下均为临时合成数据的热缓存中位耗时，保留正常垃圾回收。服务基准 21 轮交错执行，并在完整测试结束后单独重跑；Store 基准 30 轮交错执行。机器上仍有正常应用运行，耗时不能视作固定性能承诺。

| 场景 | 旧路径 → 当前路径 | 确定性变化 |
|---|---|---|
| 2,000 条矩阵，共用一个项目 | 17.692 → 7.780 ms | SELECT 2,001 → 2；项目正文解码 2,000 → 1 |
| 4,000 条配置，引用 20 个矩阵 | 27.344 → 3.395 ms | SELECT 8,001 → 22；仅保留矩阵可见性布尔值，避免缓存完整诊断 |
| 全部 2,000 条导入，选中项目 20 条 | 3.629 → 0.129 ms | 导入正文解码 2,000 → 20；仍保留逐项授权，SELECT 均为 22 |
| 20,000 个任务，全局汇总 | 0.773 → 0.555 ms | SELECT 12 → 3；新旧均不解码正文 |
| 同一任务库，单项目 200 条 | 0.0433 → 0.0195 ms | SELECT 12 → 3；结果逐项相等 |
| 10,000 个矩阵关联 50 行任务 | 1.295 → 0.469 ms | 包含 Map 构建；从逐行扫描改为一次建索引和按键查找 |

早期非交错汇总诊断曾出现聚合耗时回退，因此不以查询数量下降推导恒定加速。曾发现独立 Store 脚本加载已安装旧包，已修正脚本工作区导入、补充源码来源/SHA（文件内容校验值）及查询数断言，旧误加载结果已废弃。

- 后端全套：**856 passed、23 skipped**，4 条测试警告；日志 `backend-tests.log`。
- 前端全套：**72 passed、0 failed**；生产构建通过。独立复核另覆盖存储、权限、导入及事务。
- 阻塞提交回归在临时 ASGI（异步 HTTP 服务调用接口）环境中使用可控等待：等待期间身份请求先完成，提交最后仍返回 QUEUED，调用者身份完整保留。它不衡量磁盘吞吐，数据库请求仍可能等待服务锁。
- 保存 SQLite 备份后，以原进程环境重启本地服务；新进程 `81309`，健康检查正常。5 个读取接口的完整响应与重载前逐项校验一致，浏览器已重载新构建，任务矩阵名称正常且未见错误日志。
- **121 个实体、528 条事件、94 条审计及数据库结构全部保持**。8 个冻结发布/依赖/公开数据文件与原发布清单哈希一致，数值模块保持原内容。

本轮交付为工作副本及本地运行服务。原 0.9.0 冻结归档保留原内容，尚不包含本轮补丁；后续正式发布应另行打包并验证全新环境安装。
